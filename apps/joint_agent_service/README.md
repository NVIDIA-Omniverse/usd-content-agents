# Joint Agent Service

> **Status: Research Preview (0.5).** Owned-core USDZ publication verifies the
> authored joint graph against accepted structured input. It does not guarantee
> correct inference, complete simulation schemas, or dynamic behavior.

FastAPI service for Joint Agent classification, candidate inference, and
owned-core USDZ publication.

## Quickstart

Set `NVIDIA_API_KEY` and `RENDER_ENDPOINT` in the repo-root `.env`, then run:

```bash
docker compose --env-file .env \
  -f apps/joint_agent_service/docker-compose.yml up --build
```

The public service defaults to `nim`, `qwen/qwen3.5-397b-a17b`, and remote
rendering through `RENDER_ENDPOINT`. Uploads have no fixed size cap by default;
operators can set a positive `JA_MAX_UPLOAD_SIZE_MB` guard.

> **Status: Research Preview (0.5).** A successful request can publish a
> self-contained USDZ package whose readback matches the accepted structured
> joint graph. It does not guarantee simulation-ready output. Generated
> packages may lack complete rigid-body, mass/collider, joint-state, or
> drive/mimic schemas, can fail Gate 3 validation, and may not
> simulate correctly. Validate each output before simulation use.

## Run Locally

From the repository root:

```bash
docker compose --env-file .env \
  -f apps/joint_agent_service/docker-compose.yml up --build

curl http://localhost:8000/health
```

Use `apps/joint_agent_service/client/client.py` or the `joint-agent-client`
skill to submit and monitor a USD-family asset.

## Client-supplied S3 inputs

Client-supplied `s3_uri` inputs are disabled until the deployment configures an
explicit bucket allowlist:

```bash
JA_S3_ALLOWED_BUCKETS=your-dedicated-intake-bucket
```

The value is a comma- or whitespace-separated list of exact bucket names. It
does not accept `s3://` URIs, wildcards, or key prefixes, and this policy does
not impose application-level key-prefix restrictions. An empty or unset value
fails closed: every client-supplied S3 URI receives the same generic HTTP `403`
before any S3 request. Direct uploads and existing-session inputs are
unaffected.

Before upgrading a deployment whose clients use `s3_uri`, set the allowlist or
migrate those clients to direct uploads. Leaving it unset intentionally changes
all S3 URI requests to `403`; restart the service after changing the setting.
The Helm chart exposes the same setting as `s3AllowedBuckets`.

Because allowing a bucket authorizes every key in that bucket at the
application layer, use a dedicated intake bucket rather than one that contains
unrelated or sensitive objects. Restrict the service IAM role to only the
required bucket and prefixes as defense in depth; IAM scoping does not replace
this request-authorization policy.

## Research Preview Joint Rigger

Joint Rigger application is opt-in. Submit `apply_joint_rigger=true`; when
`joint_rigger_adapter` is omitted, the service selects the built-in
`owned_core` adapter and publishes `cache/joint_rigger/rigged.usdz`.

```bash
curl -fsS -X POST http://localhost:8000/pipeline \
  -F "usd_file=@scene.usdz" \
  -F "apply_joint_rigger=true"
```

The normal service pipeline supplies `owned_core` with consistent Stage 1
prediction JSONL and accepted Stage 2 articulation candidates. Both
contract-derived paths author accepted joint topology and source-backed limits.
For aggregate or multi-root contracts, V2 additionally authors exact aggregate
rigid-link membership and articulation roots; ordinary one-root existing-link
contracts retain V1. Candidate-only CLI/YAML compatibility calls may omit
predictions and retain the transitional Stage 2-only path. Generated service
configs set `apply_masses=false` and `apply_collision=false`; explicit `true`
requests are rejected. Service-generated candidates are limited to revolute and
prismatic joints because the 0.5 owned bridge does not support spherical
topology. Empty or all-unready candidate sets complete without a package. The
Research Preview does not claim rigid-body, mass, collision, drive, joint-state,
mimic, or simulation-readiness authoring. The public path uses `owned_core` and
has no external-rigger fallback.

New owned-core output downloads use
`GET /artifacts/{session_id}/joint-rigger-output` with filename `rigged.usdz`.
Completed results include `joint_rigger_artifact_keys`, and reused sessions
resolve only immutable keys under that run's publication directory. The
endpoint retains USDZ-first read compatibility only for legacy completed
sessions that predate that binding metadata. Each non-empty publication also
has an opaque `joint_rigger_publication_id`; downloads open a stable byte
snapshot and verify that identity again before returning it, so concurrent
reruns cannot replace the selected bytes.

Raw USD generated by the optional external adapter is validated with its source
dependency closure and packaged as `rigged.usdz` before the immutable download
key is committed. Publication directories from superseded reruns are retained
until the session is deleted. Deployments should run session TTL cleanup or
delete expired sessions; automatic per-rerun publication pruning remains
post-0.5 work. Dataset and prediction prerequisites use the same generation-bound
publication and retention policy under `artifacts/run_cache/`; regeneration and
downloads resolve the generation selected by completed session metadata. A second
run for the same session is rejected with HTTP 409 while the accepted run still
owns its cross-instance claim.

On-demand reports for pre-binding legacy sessions use a separate immutable key
under `artifacts/prediction_reports/` and an atomic metadata binding. This avoids
copying the full dataset/prediction cache solely to publish one HTML report.

## Validate Output

After downloading the final Joint Rigger USD/USDZ, use the bundled
`joint-agent-validation` skill to run optional Gate 3A and Gate 3B checks. The
validation reports are diagnostics and do not alter the service output.
Both gates are static checks; a pass does not replace dynamic simulation
testing. Use `validation-agent-cli` for separate visual or behavior-evidence
validation.
